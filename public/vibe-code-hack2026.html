What we're building, and the two prompts that build it

What we're building today

Everyone builds the same app, so the hour stays on the rails: a prayer wall where people sign in, post a request, upvote the ones they've prayed for, comment, and report anything off — with an admin view to act on those reports.

Look at how Prompt 1 is written. It names who signs in, what they can do, and what the admin sees. That level of detail is why it produces a working app instead of a vague one — and it's the habit to copy when you write your own.

Your own idea comes next time. Write it in the same shape: who it's for, what they can do, what gets kept.

How to use these two prompts

Prompt 1 builds the whole app. Paste it, then leave it alone while it works — it installs a lot.

Prompt 2 puts it on the internet, once the app runs on your own machine.

Between the two you do the part the AI can't: run its .sql file in Supabase and paste in your real keys. The steps below say when.

Prompt 1 · Step 2 — build the whole thing 
Make me a webapp in this folder and start it up so I can see it in my browser. Use Next.js with the App Router and TypeScript and the backend with Supabase.

Here is what the webapp is:
Prayer wall for users to view or post prayer requests. Include function to upvote when they prayed and other social elements such as commenting and community reporting. Users have to login via email and password via Supabase to post/edit/delete their posts. Admin will be able to see community reports and archive/hide/delete a post.

Connect the webapp to my Supabase database:
- Install whatever Supabase needs
- Generate all the sql tables and queries for my webapp in a single .sql file for me to paste into Supabase
- Generate all the keys in a file called .env.local, named NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY — read them from there and never put them in the code

If something goes wrong saving, put a clear message on the screen so I can see it. Do not let it fail quietly. When it is running, tell me the address to open.

Two things to do while it builds. It writes .env.local with the key names but it cannot know your actual keys — paste those in yourself from Supabase → Project Settings → API, then restart the server. And when it finishes the .sql file, open it, copy all of it into Supabase → SQL Editor → Run. The app won't work until both are done.

Prompt 2 · Step 5 — push and deploy

It will stop and ask you things — to sign in to GitHub or Vercel, to name the repo, to approve a command. Answer each one and let it carry on. If it can't finish the Vercel part itself, do those steps in your browser — they're on the cheat sheet further down.

Get this project onto GitHub so I can deploy it. After pushing to Github, connect it to Vercel and deploy it.

Key concepts — what each piece is doing

Four tools, one pattern: the AI writes and automates; you install, paste and sign in. Every piece below has a part it does for you and a part only you can do.

Next.js

The app people see and use

Next.js and its component libraries handle the whole user interface — the pages, the forms, the buttons, what happens when someone clicks. Once Claude or Cursor has generated the code, there is nothing to design or wire by hand.

Your partInstall it with npm install — usually the AI has already done this for you — then run npm run dev to see it in your browser.

Supabase

The database and the logins

Supabase provides the ready-made functions your app calls: signing people in, saving a post, reading them back. It hosts the database too, so nothing lives on your laptop.

Your partTwo things. Paste your Project URL and API key (the anon one) into .env.local so the app can find your database. Then open the .sql file the AI generated — usually in a /supabase folder — and copy, paste and run it in Supabase yourself. The AI cannot run it for you.

GitHub

Where the code lives

All your code is committed to GitHub as the one central copy. That is what gives you version control — every change is recorded, so a mistake is something you can walk back from rather than lose work to.

Your partSign in first. The AI can then automate the rest through the GitHub command line tool (the CLI), but it cannot log in as you.

Vercel

What puts it on the internet

Vercel takes the code from your GitHub repository and serves it from a real web server, so your app has an address anyone can open. After the first setup, every push to GitHub redeploys it automatically.

Your partSign in first, here too. The AI can drive the Vercel CLI once you have — and remember your keys need adding in Vercel separately, since .env.local never leaves your laptop.

Your cheat sheet — pre-work, keys and deployment

Before you arrive — all of it

Every link is in the appendix at the end.

  • Node.js installed — the LTS version from nodejs.org
  • Cursor installed and signed in at least once
  • GitHub account, signed in on this laptop
  • Vercel account — sign up with GitHub
  • Supabase project created — the project itself, not just the account. It takes a few minutes to start up, so do not leave this to the day.
  • Keys copied into a notes file: Project Settings → API → the Project URL and the anon public key

Manage and Protect Your Keys — in two places

  • On your laptop: make a file called .env.local in the project folder with two lines — NEXT_PUBLIC_SUPABASE_URL= and NEXT_PUBLIC_SUPABASE_ANON_KEY= — then restart the server. Keys only load when it starts.
  • In Vercel: the same two lines go in Settings → Environment Variables before you deploy. .env.local never leaves your laptop, so Vercel cannot see it.
  • The anon key is meant to be public — it is safe in a browser. The service_role key on that same Supabase page is not. Don't touch it today.

If it can't do the Vercel part

Prompt 2 will try. If it gets stuck or asks you to, do it yourself — it's five clicks.

  • Go to vercel.com → Add New → Project
  • Pick the repo it just pushed → Import
  • Add your two keys under Environment Variables, before deploying
  • Click Deploy and watch it build (about a minute)
  • Open the link, sign up, post something. That is your app, live, with real accounts and real data.
  • Every push to GitHub redeploys it automatically from now on

Appendix — everything to install and sign up for

Do all of this before the session. Two or three downloads, three accounts, about twenty minutes — but the Supabase project takes a few minutes to start up on its own, so don't leave it to the morning of.

Install on your laptop

Node.js, plus one AI coding tool

Node.js — the LTS version nodejs.org/en/download Nothing else works without this. Take the one marked LTS, not Current, and accept every default in the installer. To check it worked, open a terminal and type node --version — a number means you're done. Claude — desktop app claude.com/download The desktop app lets you use Claude Code without the terminal. Needs a paid Claude plan — Pro or above; the free plan doesn't include Claude Code. If you already pay for Claude, use this. If not, use Cursor below. Prefer the terminal? curl -fsSL https://claude.ai/install.sh | bash on Mac or Linux, or irm https://claude.ai/install.ps1 | iex in Windows PowerShell. Cursor — AI code editor cursor.com Has a free tier that's plenty for today, so this is the one to get if you're not already paying for Claude. Download, install, and sign in at least once before the session. You only need one of the two Claude or Cursor — both run the same prompts and work the same way. We'll demo in Cursor; if you're on Claude, everything still applies.

GitHub

Where your code lives

Create an account github.com/signup Free. Use an email you can check during the session — it sends a verification code. Stay signed in on the laptop you're bringing. Already have one? github.com/login Just confirm you can sign in. A forgotten password is a slow thing to fix with a room waiting.

Vercel

What puts it on the internet

Sign up — with GitHub vercel.com/signup Choose Continue with GitHub, not email. It links the two accounts straight away, which is what lets Vercel see your repositories later. Take the free Hobby plan — no card needed.

Supabase

Your database and logins

Sign up supabase.com/dashboard/sign-up Continue with GitHub is quickest. Free tier, no card. Then create a project — not just the account supabase.com/dashboard/new Name it anything. Save the database password it asks you to set. Pick the region nearest you — Singapore if you're here. It then takes a few minutes to start up, which is why this can't wait until the session. Copy your two keys into a notes file Project Settings → API You need the Project URL and the anon public key. Ignore service_role — that one bypasses every security rule and is not for today. Turn off email confirmations (optional) Authentication → Sign In / Providers → Email Switch off Confirm email. Leave it on and you'll sit waiting for a confirmation mail just to sign into your own app. Turn it back on before real people use it.
