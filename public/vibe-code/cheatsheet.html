The stack — what each thing actually does

Cursor

Where you write

Your editor. You describe what you want in plain English; it writes and edits the code with you.

Next.js

The app itself

The framework your app is built on. A folder becomes a page. app/about/page.tsx → /about.

Supabase

Memory + logins

Your database and your sign-in system. Where a form submission goes so it's still there tomorrow.

GitHub

The safety net

Every version of your code, saved off your laptop. Break something? You can always go back.

Vercel

The front door

Puts your app on the internet. Push to GitHub and it rebuilds and redeploys on its own.

Resend

The messenger

Sends real email from your app — a welcome note, a confirmation, an alert to you when someone signs up.

Your first edit — point at it in the browser

  1. Get the app running. npm run dev must be live at localhost:3000 first.
  2. Open Cursor's Browser and point it at your app. Keep it in the pane inside Cursor — select element stops working if you pop the browser into a separate window.
  3. Click Select element — the pointer icon in the browser toolbar. Hover the page and elements light up one by one.
  4. Click the thing you want to change. It's attached to the chat as context, so Cursor already knows which component and file it came from. You never type a file path.
  5. Describe the change in plain English and send it. Click one element at a time — clicking five floods the chat and Cursor loses the target.

Connecting Supabase — keys, env file, tables

StepWhat to do
Get your three values Supabase dashboard → Project Settings → API. Copy the Project URL, the anon public key, and the service_role key.
Make the env file In your project root — the folder with package.json — create a file called .env.local.
Paste them in NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGc...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGc...No quotes, no spaces around the =. Only the first two get NEXT_PUBLIC_ — that prefix means "send to the browser", which the service_role key must never be.
Restart the server Keys only load at startup. Ctrl+C, then npm run dev.
Ask Cursor for the SQL “Write the SQL to create a prayers table with id, name, message and created_at, with Row Level Security enabled and a policy that lets signed-in users read and insert.”
Run it in Supabase Dashboard → SQL Editor → New query → paste → Run. Then open Table Editor to see the table exists.
Keep the SQL Save it in your repo as schema.sql. It's how you rebuild the database if you ever start a fresh project.

Connecting Vercel — repo, region, keys, logs

StepWhat to do
Link your GitHub repo vercel.com → Add New → Project → choose your repo → Import. Vercel spots that it's Next.js and fills in the build settings itself. Every push to your main branch now rebuilds automatically.
Pick your region Settings → Functions → Function Region → Singapore (sin1). Choose the one nearest your users, and match it to your Supabase region so the two aren't talking across the planet.
Copy your keys across (or generate new keys for Production) Settings → Environment Variables. Open .env.local, add each line as a Name / Value pair, tick Production. Your .env.local never leaves your laptop — Vercel has no idea it exists unless you do this.
Redeploy New keys only apply to new builds. Deployments → latest → ⋯ → Redeploy.
Watch the build The Deployments screen shows Building, then Ready or Error. Click any deployment to open its Build Logs.
If it says Error Open Build Logs, scroll to the red line, copy it, paste it into Cursor and ask why the build failed.

Asking Cursor for things — say what you'd see, not how to code it

"Make a useState hook and a handler"

"When someone types their email and clicks Join, save it to Supabase and show 'You're on the list'."

"Fix my app"

"The Join button does nothing. Here's the whole error from the terminal: …"

Paste the entire error, not your summary of it. The part you'd skip is usually the part that matters.

  • Tell it the stack once per chat. "Next.js App Router, TypeScript, Tailwind, Supabase."
  • One change at a time. Five requests in one message gets you five half-done things.
  • Check it after every change. Look at the browser before you ask for the next thing.
  • Ask it to teach you. "Explain this file to me like I've never seen React." That's a normal thing to ask.
  • Going in circles? Start a fresh chat. A long confused conversation stays confused.

When it breaks — work down this list before asking for help

CheckWhat to do
Did you save the file? Genuinely the most common one. Save, then look again.
Read the error, last line first It usually names the file and the line number.
Is npm run dev still running? Check the terminal tab — it may have stopped.
Restart it In your terminal, press Ctrl+C, then run npm run dev again.
Still nothing obvious? Paste the full error into Cursor chat and ask why it's happening.
Added a new key to .env.local? Restart the server. Keys only load at startup.
Still odd? Stop the server with Ctrl+C, clear the cache by running rm -rf .next, then start up again with npm run dev.
Works locally, broken on Vercel? Your keys could be missing in Vercel. Set up the keys in Environment Variables, then redeploy. Alternatively, go to Deployment logs, copy the error and paste it in Cursor to fix.
Data won't load and there's no error? Possible causes: Row Level Security is on with no policy. That's Supabase doing its job — write the policy. Also, did you check your Supabase keys are set in .env?
Still stuck after 15 minutes? Post it in the group chat with the error and what you already tried. That's the job, not a failure.

Three things to never do (for security reasons)

Never commit .env.local. Check that .gitignore lists it before your first push.

Never put the Supabase service_role key in front-end code. The anon key is designed to be public; service_role bypasses every security rule you've written. Server-side only.

Never leave a table with Row Level Security switched off. Off means anyone with your public key can read and rewrite it.
